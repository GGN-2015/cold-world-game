## 命令行参数

`uv run cold-world-game` 与 `uv run python -m cold_world_game` 等价；追加 `--help` 查看帮助。Windows PowerShell 和 Linux shell 使用相同参数，不需要平台专用启动脚本。

| 参数 | 默认值 | 用途 |
| --- | --- | --- |
| `--host` | `127.0.0.1` | 监听地址，局域网联机用 `0.0.0.0` |
| `--port` | `5000` | 0～65535；0 表示自动分配，终端输出实际端口 |
| `--password` | 每次启动随机生成 | 共享游戏口令，不允许空字符串；固定口令须显式传入 |
| `--save-path` | `~/.cold-world-game` | 存档目录或 `.db` / `.sqlite` / `.sqlite3` 文件路径 |
| `--seed` | 新世界随机种子 | 只影响新建世界；加载已有存档时保留原种子 |
| `--allowed-origin` | 仅同源 | 可重复添加允许连接的额外浏览器 Origin，不是访问口令 |
| `--log-level` | `INFO` | `DEBUG` / `INFO` / `WARNING` / `ERROR` |

```sh
uv run cold-world-game --host 0.0.0.0 --port 5000 --password your-server-password --save-path ./saves --log-level INFO
```

## 备份与更新

1. 在服务器终端按 Ctrl+C，等待正常保存并退出。
2. 备份整个存档目录，保留原数据库；不要在服务器运行时只复制 `.sqlite3` 主文件而忽略 WAL。
3. 更新程序，在原项目目录执行 `uv sync --frozen`，使用原来的 `--save-path` 启动。
4. 使用原名字确认个人状态和旧建筑正常；到尚未生成的区域探索新版内容。旧区块不会刷新急救包、回城法杖或机器。

新增字段均提供旧存档缺省值；不删除存档、不更换种子、不重建已有区块。地图以区块生成版本为准，当前第 6 版，详细边界见 [世界与地图](world.md)。急救包使用时，物品消耗、体温与饥饿恢复一起保存，失败则全部回退。回城法杖沿用物品 `uses` 保存次数；缺失次数时缺省为 20，已有剩余次数绝不补满。传送、扣次与必要新区块在同一事务内保存。

遇到存档被占用，先确认没有第二个服务器进程打开同一世界。写盘失败会暂停世界并输出错误；保留数据库，排查磁盘空间、权限和存储设备后再重启。不要通过删除世界解决故障。

## 服务器逻辑
游戏服务器是一个 HTTP 服务器，玩家使用浏览器访问游戏服务器。玩家最开始的时候需要输入一个自己的 ID 以及服务器密码。这个服务器密码是由服务器启动时设定的。浏览器会缓存玩家上次登录所使用的用户 ID 以及口令。玩家点击进入游戏时，如果相同 ID 的玩家在游戏中已经存在，则玩家不能进入游戏。

每个浏览器窗口进入游戏后，玩家 ID 绑定到该窗口自己的连接。另一个窗口使用不同 ID 登录或更新浏览器缓存，不会切换已登录窗口的玩家身份，因此同一个浏览器可以用多个窗口同时控制不同 ID。

玩家第一次进入游戏时，会从区块 (0, 0) 中随机选择一个可落脚的位置出生，而不是固定出生在世界坐标 (0, 0)。可落脚位置要求玩家的碰撞箱不与树、墙、柱子、栅栏、箱子、篝火等障碍物重叠，并且能够通向建筑开口。新玩家的初始饥饿值为 10，初始体温为 36 度。

玩家每次掉线时，服务器会记录玩家掉线前最后时刻的坐标、物品栏、背包、饥饿值、温度值、物品剩余子弹数和使用次数等状态，然后立即将玩家实体从世界中移除。离线玩家对任何人都不可见，不参与碰撞、怪物索敌和伤害判定；离线期间不消耗饥饿值、温度值或随身物品，也不随时间恢复体温，个人状态保持不变。玩家下一次进入时恢复记录的坐标和状态；如果原位置已被其他玩家放置的障碍物占用，则只将位置调整到附近最近的可落脚位置。只要仍有其他玩家在线，单个玩家离线不会暂停世界时间，也不会暂停已放置的火堆燃烧。

服务端的启动是命令行的，命令行中可以指定服务器密码以及游戏存档的保存路径。如果不指定的话，游戏会有一个默认的存放保存路径。如果指定的游戏存档保存路径中已有存档，则游戏会加载这个旧的存档。游戏过程中会在合适的时候实时存档以防止游戏数据丢失。

没有通过命令行传入服务器口令时，每次启动生成一个新的随机口令并显示在终端；存档中不保存口令。柱子本质上就是一格木墙，生成、碰撞、拆除与掉落均直接使用木墙规则，不作为独立建筑类型。

服务器在至少一名玩家在线时以每秒 20 个 tick 更新游戏逻辑，移动、温度和饥饿值均按实际经过的时间结算。浏览器计算本机移动与碰撞并上报位置，服务器汇总位置、统一结算怪物、命中、冷却、材料消耗与物品转移；同一物品不能被多个玩家同时取走。

物品栏、背包、箱子、火堆和地面之间的每次物品转移都必须原子保存：来源中的物品扣除、目标中的物品写入，以及数量、所在格子、剩余子弹数、使用次数、火堆缓存木材和地面掉落物的创建或删除等相关状态，作为同一次操作一起提交，不能拆成互不关联的存档更新。服务器只在原子保存成功后确认转移成功。恢复存档时，要么整次转移生效，要么整次回退；掉线或服务器崩溃都不能造成同一物品在两处同时存在，或从两处同时消失。

浏览器在物品栏、背包与箱子之间移动物品时立即显示转移预览，支持连续整理，不锁住整个操作面板，也不额外等待下一份快照。多个尚未确认的转移按发送顺序预览，旧快照不会把已移动的物品闪回原处；服务器确认后由带命令序号的快照接管显示。容量不足、来源已被其他玩家取走、保存失败或断线时撤销相应预览，以服务器实际结果为准，客户端预览不创建真实物品或改变原子保存规则。物品格复用原有 DOM 节点，确认时不会重建整个背包或箱子，保持滚动位置与焦点；手机整理操作使用同样的机制。

最后一名玩家离线后，服务器立即保存并暂停整个世界模拟：游戏时间和季节不推进，火堆不消耗燃料，怪物和在途子弹保留原位，所有世界计时器冻结，不进行怪物生成、移动、攻击或距离清理。第一名玩家重新进入时，先恢复玩家实体，再恢复世界模拟，并按在线玩家重新判定怪物目标；暂停期间经过的现实时间不补算。服务器关闭期间也按暂停处理，重新启动只加载已保存的状态。文中消耗、恢复、移动和冷却涉及的现实时间，均只累计世界正在运行的时间。

## 服务端与存档

也可以执行 `uv run python -m cold_world_game`，使用 `--help` 查看完整参数。`--seed` 只影响新世界，旧存档始终优先；`--allowed-origin` 可重复指定允许连接的额外浏览器 Origin，例如 `--allowed-origin http://localhost:5173`。

默认存档是用户主目录下的 `.cold-world-game/world.sqlite3`：Windows 通常位于 `C:\Users\用户名\.cold-world-game\world.sqlite3`，Linux 通常位于 `/home/用户名/.cold-world-game/world.sqlite3`。`--save-path` 支持目录，也支持 `.db`、`.sqlite`、`.sqlite3` 文件路径。相同存档只能被一个服务进程打开。

物品操作通过 SQLite 事务原子提交世界状态，成功落盘后才确认；其他连续状态每累计运行 2 秒保存一次，登录、掉线、全员退出和正常关闭也会保存。写盘失败会回滚本次物品操作并暂停世界，终端输出错误，排查磁盘问题后重新启动。按 Ctrl+C 正常退出；备份存档前应先停止服务器，运行时不要只复制主文件而遗漏 SQLite 的 WAL 文件。

存档格式第 2 版将世界状态分区保存在 `world_parts` 中，建筑再按实体 ID 单独存储：未变化的建筑不重复 JSON 编码和写盘，一堆篝火燃烧或一个箱子换物也不再重写整图。变化的建筑、玩家、怪物、子弹、物品等仍在同一个 SQLite 事务中一起提交。继续使用 WAL 和 `synchronous=FULL`；不延迟物品操作确认，不牺牲断电持久性，提交失败也不会更新增量保存缓存。第 1 版整图 JSON 存档可直接加载，首次保存时在同一事务内升级；迁移失败保留原存档。升级保留种子、物品 ID、旧建筑和区块版本，不重刷地图。升级后的存档需用新版程序读取；如需退回旧程序，使用升级前的完整备份，不要让旧程序直接读取第 2 版。

`GET /` 返回可游玩的浏览器页面，`GET /api/server` 返回服务信息，`GET /health` 返回健康状态，`GET /api/info` 返回配方和规则目录，实时接口为 `/ws`；消息格式见 [接口协议](protocol.md)。浏览器负责本机移动碰撞与远端运动显示，服务器接受并汇总本机位置，负责世界、怪物决策、物品事务、体温、命中与射速等共同状态；物品和金钱仍须原子落盘后确认。此模式面向可信的私人联机，不提供移动速度反作弊。

服务器面向小型私人联机，单进程运行一个世界，不使用多进程 WSGI worker 或自动重载。命令行采用带线程的 Werkzeug 服务器以支持两个平台的 WebSocket。对公网开放时应在前面配置 HTTPS/WSS 反向代理及连接限制；游戏口令不是离线玩家 ID 的所有权凭据，仍按本文原先的共享口令规则登录。

## 多怪战斗性能

密集战斗的优化针对两个实际瓶颈：服务器同步完成多次复杂 A* 导致模拟与状态发送长时间等待，以及每次射击、命中都重复序列化和写入未变化的整张地图。现在寻路可暂停并轮转续算，每 tick 共享约 8 毫秒搜索预算，保存仅写变化的状态分区。怪物移动、攻击、冷却、碰撞和伤害规则不变，浏览器继续使用逐帧运动显示，不把怪物移成瞬移，也不通过降低射速或关闭保存来换取性能。

2026-11-11 的隔离压力测试持续维持 70 只怪物、真实寻路与攻击、玩家长按步枪连射并正常 SQLite 落盘，分别运行桌面浏览器和 4 倍 CPU 降速的手机视口。优化前状态更新曾间断约 0.8 秒；优化后平均恢复到约 100 毫秒，常规更新间隔的 95% 约在 140 毫秒以内。延长测试也观察到偶发的磁盘提交延迟，因此客户端对短暂缺少新状态的远端实体保持最多 0.3 秒匀速推算，然后平滑减速；推算仍校验建筑碰撞，0.5 秒未收到状态时停止，伤害与物品只认服务器结果。这些数字是该测试环境的观测值，不是所有设备的帧率保证；更新后需要重启后端并刷新游戏页面才会运行新版逻辑。
