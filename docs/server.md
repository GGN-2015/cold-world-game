## 命令行参数

`uv run cold-world-game` 与 `uv run python -m cold_world_game` 等价；追加 `--help` 查看帮助。Windows PowerShell 和 Linux shell 使用相同参数，不需要平台专用启动脚本。

| 参数 | 默认值 | 用途 |
| --- | --- | --- |
| `--host` | `127.0.0.1` | 监听地址，局域网联机用 `0.0.0.0` |
| `--port` | `5000` | 0～65535；0 表示自动分配，终端输出实际端口 |
| `--password` | 每次启动随机生成 | 共享游戏口令，不允许空字符串；固定口令须显式传入 |
| `--admin` | 不启用玩家管理员 | 唯一管理员玩家 ID；只对本次启动生效，见 [管理员命令手册](admin.md) |
| `--save-path` | `~/.cold-world-game` | 存档目录或 `.db` / `.sqlite` / `.sqlite3` 文件路径 |
| `--seed` | 新世界随机种子 | 只影响新建世界；加载已有存档时保留原种子 |
| `--allowed-origin` | 仅同源 | 可重复添加允许连接的额外浏览器 Origin，不是访问口令 |
| `--log-level` | `INFO` | `DEBUG` / `INFO` / `WARNING` / `ERROR` |

```sh
uv run cold-world-game --host 0.0.0.0 --port 5000 --password your-server-password --save-path ./saves --log-level INFO
```

## 备份与更新

1. 在服务器终端按 Ctrl+C，等待正常保存并退出。
2. 备份整个存档目录，保留原数据库；不要在服务器运行时只复制 `.sqlite3` 主文件而忽略 WAL。
3. 更新程序，在原项目目录执行 `uv sync --frozen`，使用原来的 `--save-path` 启动。
4. 使用原名字确认个人状态和旧建筑正常；到尚未生成的区域探索新版内容。旧区块不会刷新急救包、回城法杖或机器。

新增字段均提供旧存档缺省值；不删除存档、不更换种子、不重建已有区块。地图以区块生成版本为准，当前第 9 版，详细边界见 [世界与地图](world.md)。急救包使用时，物品消耗、体温与饥饿恢复一起保存，失败则全部回退。回城法杖沿用物品 `uses` 保存次数；缺失次数时缺省为 20，已有剩余次数绝不补满。传送、扣次与必要新区块在同一事务内保存。

寒冰法杖同样使用 `uses` 保存剩余次数，缺失时默认为 100，已有次数原样保留。怪物新增的 `frozen_until` 是世界运行时间的绝对截止值，旧存档缺失时默认为 0（未冰冻）。法杖扣次、怪物伤害与冰冻、死亡与掉落一起提交；空间不足的物品转移或保存失败均保持整次操作前的状态。退出和重启不会补算冰冻时间，也不会补充法杖次数。

遇到存档被占用，先确认没有第二个服务器进程打开同一世界。写盘失败会暂停世界并输出错误；保留数据库，排查磁盘空间、权限和存储设备后再重启。不要通过删除世界解决故障。

第 8 版新增内容同样不重刷旧区块。烈焰法杖缺失 `uses` 时默认为 100，已有剩余次数保持不变；怪物灼烧截止时间、下次跳伤害时间与来源均提供无灼烧缺省值。投出的炸弹使用原投射物集合保存起落点和到达时间，旧子弹缺省为 `kind:bullet`，其余新字段为空。金币消耗、物品消耗、伤害、灼烧、爆炸、死亡和掉落遵守原子提交；离线和服务器停机均冻结计时，恢复不补算，不重复爆炸或生成内容。

## 服务器逻辑
游戏服务器是一个 HTTP 服务器，玩家使用浏览器访问游戏服务器。玩家最开始的时候需要输入一个自己的 ID 以及服务器密码。这个服务器密码是由服务器启动时设定的。浏览器会缓存玩家上次登录所使用的用户 ID 以及口令。玩家点击进入游戏时，如果相同 ID 的玩家在游戏中已经存在，则玩家不能进入游戏。

每个浏览器窗口进入游戏后，玩家 ID 绑定到该窗口自己的连接。另一个窗口使用不同 ID 登录或更新浏览器缓存，不会切换已登录窗口的玩家身份，因此同一个浏览器可以用多个窗口同时控制不同 ID。

玩家第一次进入游戏时，会从区块 (0, 0) 中随机选择一个可落脚的位置出生，而不是固定出生在世界坐标 (0, 0)。可落脚位置要求玩家的碰撞箱不与树、墙、柱子、栅栏、箱子、篝火等障碍物重叠，并且能够通向建筑开口。新玩家的初始饥饿值为 10，初始体温为 36 度。

玩家每次掉线时，服务器会记录玩家掉线前最后时刻的坐标、物品栏、背包、饥饿值、温度值、物品剩余子弹数和使用次数等状态，然后立即将玩家实体从世界中移除。离线玩家对任何人都不可见，不参与碰撞、怪物索敌和伤害判定；离线期间不消耗饥饿值、温度值或随身物品，也不随时间恢复体温，个人状态保持不变。玩家下一次进入时恢复记录的坐标和状态；如果原位置已被其他玩家放置的障碍物占用，则只将位置调整到附近最近的可落脚位置。只要仍有其他玩家在线，单个玩家离线不会暂停世界时间，也不会暂停已放置的火堆燃烧。

服务端的启动是命令行的，命令行中可以指定服务器密码以及游戏存档的保存路径。如果不指定的话，游戏会有一个默认的存放保存路径。如果指定的游戏存档保存路径中已有存档，则游戏会加载这个旧的存档。游戏过程中会在合适的时候实时存档以防止游戏数据丢失。

没有通过命令行传入服务器口令时，每次启动生成一个新的随机口令并显示在终端；存档中不保存口令。柱子本质上就是一格木墙，生成、碰撞、拆除与掉落均直接使用木墙规则，不作为独立建筑类型。

服务器在至少一名玩家在线时以每秒 20 个 tick 更新游戏逻辑，移动、温度和饥饿值均按实际经过的时间结算。浏览器计算本机移动与碰撞并上报位置，服务器汇总位置、统一结算怪物、命中、冷却、材料消耗与物品转移；同一物品不能被多个玩家同时取走。

物品栏、背包、箱子、火堆和地面之间的每次物品转移都必须原子保存：来源中的物品扣除、目标中的物品写入，以及数量、所在格子、剩余子弹数、使用次数、火堆缓存木材和地面掉落物的创建或删除等相关状态，作为同一次操作一起提交，不能拆成互不关联的存档更新。服务器只在原子保存成功后确认转移成功。恢复存档时，要么整次转移生效，要么整次回退；掉线或服务器崩溃都不能造成同一物品在两处同时存在，或从两处同时消失。

浏览器在物品栏、背包与箱子之间移动物品时立即显示转移预览，支持连续整理，不锁住整个操作面板，也不额外等待下一份快照。多个尚未确认的转移按发送顺序预览，旧快照不会把已移动的物品闪回原处；服务器确认后由带命令序号的快照接管显示。容量不足、来源已被其他玩家取走、保存失败或断线时撤销相应预览，以服务器实际结果为准，客户端预览不创建真实物品或改变原子保存规则。物品格复用原有 DOM 节点，确认时不会重建整个背包或箱子，保持滚动位置与焦点；手机整理操作使用同样的机制。

最后一名玩家离线后，服务器立即保存并暂停整个世界模拟：游戏时间和季节不推进，火堆不消耗燃料，怪物和在途子弹保留原位，所有世界计时器冻结，不进行怪物生成、移动、攻击或距离清理。第一名玩家重新进入时，先恢复玩家实体，再恢复世界模拟，并按在线玩家重新判定怪物目标；暂停期间经过的现实时间不补算。服务器关闭期间也按暂停处理，重新启动只加载已保存的状态。文中消耗、恢复、移动和冷却涉及的现实时间，均只累计世界正在运行的时间。

## 服务端与存档

也可以执行 `uv run python -m cold_world_game`，使用 `--help` 查看完整参数。`--seed` 只影响新世界，旧存档始终优先；`--allowed-origin` 可重复指定允许连接的额外浏览器 Origin，例如 `--allowed-origin http://localhost:5173`。

默认存档是用户主目录下的 `.cold-world-game/world.sqlite3`：Windows 通常位于 `C:\Users\用户名\.cold-world-game\world.sqlite3`，Linux 通常位于 `/home/用户名/.cold-world-game/world.sqlite3`。`--save-path` 支持目录，也支持 `.db`、`.sqlite`、`.sqlite3` 文件路径。相同存档只能被一个服务进程打开。

物品操作通过 SQLite 事务原子提交世界状态，成功落盘后才确认；其他连续状态每累计运行 2 秒保存一次，登录、掉线、全员退出和正常关闭也会保存。写盘失败会回滚本次物品操作并暂停世界，终端输出错误，排查磁盘问题后重新启动。按 Ctrl+C 正常退出；备份存档前应先停止服务器，运行时不要只复制主文件而遗漏 SQLite 的 WAL 文件。

存档格式第 3 版将世界状态分区保存在 `world_parts` 中，建筑按实体 ID 单独存储，并用脏对象和逐对象旧值记录完成保存及回滚：普通战斗不再遍历、复制、序列化四万座静态建筑，新增/拆除一座建筑也不再重写整个建筑 ID 索引。区块列表、区块版本和出生区域只在实际生成新区块时复制与保存，不在每次射击中重新整理。变化的建筑、玩家、怪物、子弹、物品等仍在同一个 SQLite 事务中一起提交，保持 WAL 与 `synchronous=FULL`；不延迟物品操作确认，失败也不更新保存缓存。

第 1 版整图 JSON、第 2 版分区存档（含尚未拆分的建筑数组）均可直接加载，首次保存时原子升级；迁移失败保留原格式与原内容。升级保留种子、物品 ID、旧建筑顺序、已采集对象和区块版本，不重刷地图。存档版本与地形版本不同，本次地形为第 10 版，新增箱内物品只出现在未探索的新箱子，不回填旧箱子。升级后的存档需用新版程序读取；退回旧程序须恢复升级前的完整备份，不能直接打开第 3 版存档。

`GET /` 返回可游玩的浏览器页面，`GET /api/server` 返回服务信息，`GET /health` 返回健康状态，`GET /api/info` 返回配方和规则目录，实时接口为 `/ws`；消息格式见 [接口协议](protocol.md)。浏览器负责本机移动碰撞与远端运动显示，服务器接受并汇总本机位置，负责世界、怪物决策、物品事务、体温、命中与射速等共同状态；物品和金钱仍须原子落盘后确认。此模式面向可信的私人联机，不提供移动速度反作弊。

服务器面向小型私人联机，单进程运行一个世界，不使用多进程 WSGI worker 或自动重载。命令行采用带线程的 Werkzeug 服务器以支持两个平台的 WebSocket。对公网开放时应在前面配置 HTTPS/WSS 反向代理及连接限制；游戏口令不是离线玩家 ID 的所有权凭据，仍按本文原先的共享口令规则登录。

## 多怪战斗性能

密集战斗的瓶颈包括同步复杂寻路、事务备份反复复制全图建筑和区块、网络重发静态建筑与历史事件。寻路可暂停并轮转续算，每 tick 共享约 8 毫秒搜索预算；保存与回滚只处理变化的建筑，网络首次发送附近完整状态，之后按连接发送字段差分，静态场景和碰撞网格也按变化更新。怪物决策、命中、射速、物品原子提交和落盘耐久性不变。

### 300ms 延迟与多人同行验证

2026-11-11 使用真实旧世界的只读 SQLite 备份副本：3,249 个已探索区块、测试场景清理后 39,856 个建筑、70 只持续补充的怪物、4 名同时在线玩家；两人持步枪连射，两人连续单击挥斧，运行真实怪物 AI、伤害、掉落和 SQLite 保存。四个浏览器页面同机运行，覆盖桌面、手机竖屏和横屏。TCP 代理对两个方向的数据包各延迟 150ms，HTTP 和 WebSocket 均经过代理，不是仅给 HTTP 设置延迟；游戏命令实测往返平均约 320～323ms。

| 客户端 | Canvas 绘制 P95 | 状态间隔 P95 | 本机点击至挥斧贴图 P95 |
| --- | --- | --- | --- |
| 桌面步枪 | 1.5ms | 133.7ms | — |
| 手机竖屏步枪 | 1.4ms | 142.4ms | — |
| 桌面斧头 | 1.5ms | 125.9ms | 23.8ms |
| 手机横屏斧头 | 1.5ms | 154.5ms | 27.4ms |

约 26 秒持续战斗中，四端均无超过 50ms 的浏览器主线程长任务，也未检测到远端运动显示时钟停止超过 200ms；本机刀风启动 P95 约 0.2ms，不等待往返，命中仍等待服务器。差分世界消息平均约 13.6～13.9KB，相同状态的完整消息约 49.9～50.9KB，减少约 72%～73%；怪物超出各玩家视野时正常裁剪，不强制在屏外绘制。服务器 tick 平均约 25.0ms、P95 约 33.6ms。

随后四人沿同一路线前进、转向、返回，各自实际行进约 28～40 格。逐帧跟踪全部可见玩家和怪物，排除新出现实体、倒地切换和明确的法杖传送后，没有小于 75ms 的相邻帧中超过 0.75 格的位置跳变；该场景最大玩家单帧位移约 0.27 格、怪物约 0.04 格。另以 120Hz 模拟 300ms 往返和抖动，四名同速玩家与 70 怪物的普通行走最大单帧位移约 0.041 格。

快照之间使用按实体 ID 保留的运动历史；缺包时仅进行有界推算，推算速度受角色正常速度限制，纠偏也有每帧速度上限，不将击退或输入抖动当成后续持续高速。真正断流 0.5 秒后停止远端推算；本机收到击退时立即更新逻辑坐标，但平滑修正显示，法杖传送仍按传送语义立即切换位置。表中处理耗时不代表所有设备的固定帧率保证。更新后需重启后端并强制刷新游戏页面。

寒冰法杖另在相同 3249 区块、约 3.99 万建筑、4 人与 70 怪物场景下复测，实际往返延迟均值约 322～325ms，使用两名枪手和两名寒冰法杖玩家。四端绘制 P95 为 1.5～1.6ms，挥杖到第一帧刃光的 P95 为 24.3ms（桌面）和 31.2ms（手机横屏）；均无超过 50ms 的浏览器主线程长任务或超过 200ms 的运动时钟停顿，四人同行阶段未发现普通移动跳变。冰冻只增加截止时间字段与贴图切换，怪物四向冰冻差分和八方向挥杖均为离线生成 PNG，不在运行时实时调色或重绘攻击几何。

### 新武器与管理员更新复测

2026-11-11 本次最终复测使用旧 SQLite 世界的只读备份副本：3,250 个区块、39,859 个建筑、70 只持续补充的真实 AI 怪物（包含大怪、普通小怪和快速怪）、4 人分别使用步枪、金币榴弹炮和两把烈焰法杖，同时运行投掷、爆炸、灼烧、死亡掉落与 SQLite 保存。桌面与手机横竖屏浏览器通过双向各 150ms 的真实 TCP 代理，实际命令往返均值为 319～326ms。

最终密集战斗场景的四端 Canvas 绘制 P95 均为 **1.6ms**，状态收包间隔 P95 为 127～159ms；持续战斗中本机挥杖首帧 P95 为 30.5ms（桌面）与 35.5ms（手机横屏），刀风启动 P95 为 0.3ms。没有超过 50ms 的浏览器主线程长任务，没有超过 200ms 的运动显示时钟停顿。差分消息平均 8.3～8.8KB，完整状态为 51.8～55.6KB，减少约 84%；服务端 tick P95 为 35.9ms。

四人同行、转向与返回阶段逐帧检查全部可见玩家与怪物，未发现普通移动跳变；最大玩家单帧位移约 0.33 格，怪物约 0.31 格，快速怪的更高移动速度与受击击退均包含在检查中。明确的管理员 tp 和回城法杖传送使用独立传送版本号，不误当成普通移动进行长距离插值。

另外在同样 300ms 往返下，桌面、手机竖屏与横屏分别完成武器购买、面板长按拆除、投掷取消与爆炸、榴弹炮持续扣币、烈焰法杖 100 次计数、一次性除颤救援，以及管理员 give/heal/tp、中文及带空格 ID、英文离线错误、折叠控制台与转屏操作。独立场景的本机挥杖第一帧为 3～6ms。Windows 与 Linux 均验证旧存档格式 1/2/3 加载、新区块内容、旧区域保持不变、重启不重复生成，以及交易、救援、管理员发放和传送在真实 SQLite 写入故障下整次回滚。

### 存钱罐与暖宝宝贴更新复测

2026-11-11 在 Windows 与 Linux 上验证共享余额并发存取、满背包/物品栏、非法数量和余额不足、空罐长按拆除与拆除中存入取消；暖贴 0.5 秒长按、倒地自救、保留 0/7.25/15 饥饿值，以及玩家行、容器行和掉落行真实 SQLite 写入失败的原子回滚均通过。三种旧 SQLite 格式加载保留旧区域、ID 和区块版本，新区域使用第 10 版；两次重启不补货、不重复入账。

对比更新前第 9 版生成器的 **9,401 个区块**：962 间房屋中的 51 个存钱罐精确对应独立 5% 随机流，1,477 个箱子中的 31 张暖贴精确对应独立 2% 随机流；其余旧地形、物品格和三种机器的位置保持一致。所有新罐均符合间距与容器可达性，另验证 250 个种子的原点出生通路。实测样本数量是固定种子的结果，不将其当作概率定义。

两名真实浏览器玩家在双向各 150ms 的代理下，分别于桌面、手机竖屏、横屏完成共享存取和长按拆除；他人操作更新余额不替换数量输入框、不丢失焦点。触控按钮至少 44px，转屏和中英切换均正常；暖贴成功时播放 1.4 格小型医疗 PNG，取消时不消耗。

再次使用 3,250 区块、39,859 建筑、4 人和 70 只真实 AI 怪物的密集战斗及同行场景，实际命令往返均值约 318～329ms。四端 Canvas 绘制 P95 均约 **1.6ms**；本机挥杖首帧 P95 约 32.1ms（桌面）、35.3ms（手机横屏），音效启动 P95 约 0.2ms，未检测到超过 50ms 的浏览器主线程长任务、运动时钟停顿或普通移动跳变。差分消息平均约 9.2～9.5KB，对应完整状态约 56.5～58.2KB；服务端 tick P95 约 36.0ms。存钱罐余额仅在打开容器的差分状态中同步，不加入附近全部建筑的高频序列化；暖贴复用现有特效图集，不增加逐怪物或逐建筑的帧内计算。
